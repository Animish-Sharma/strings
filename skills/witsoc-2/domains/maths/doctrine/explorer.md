# Explorer — mathematics

Loaded by the general Explorer when a claim routes to this pack. Everything in
`explorer/SKILL.md` still applies; this adds what is specific to mathematics.

## Freezing

The frozen record binds, byte-exact:

- the original problem text as the requester wrote it;
- the canonical statement, with quantifier order explicit;
- variables and their domains;
- every definition the statement depends on;
- the `GIVEN` block (hypotheses) and the `CLAIM` block, hashed separately —
  drift shows up in one or the other, and separating them says which;
- `allowed_external_facts`: results the argument may cite. A citation outside
  this list is out-of-scope, not a step.

Separate hashes matter because the characteristic failure here is a `CLAIM`
quietly weakening while the `GIVEN` stays put, or a hypothesis appearing in a
binder that was never in the frozen `GIVEN`.

Once the claim is frozen, the plan starts from it rather than from a blank file:

```bash
python3 scripts/blueprint_init.py --claim <claim.json> --out <blueprint.json>
```

Production consumes a blueprint, and before this existed the only way to get one
was to write it by hand — which meant the plan's statement and the frozen
statement were typed twice, and drift between them was a matter of typing.

## Falsify before committing

The three frame layers, instantiated:

1. **Degenerate** — empty set, singleton, zero, one, the trivial group, `n = 0`
   and `n = 1`, empty graph, constant function.
2. **Symmetry** — relabel, permute, dualize, negate, swap quantifiers, take the
   complement.
3. **Regime extremes** — both ends of every parameter, asymptotic limits,
   and the boundary where a hypothesis becomes tight.

Then check the statement against the parameter regime where the *stated
hypotheses are barely satisfied*. That is where a missing hypothesis lives.

Run the `bounded` tier on small cases before committing to any approach. It is
cheap, and a counterexample at `n = 4` saves the entire campaign.

The harness is a block in the frozen claim, not a program you write. That is the
whole on-ramp:

```json
"frozen_conditions": {
  "bounded_search": {
    "variables": [{"name": "n", "lower": 1, "upper": 12},
                  {"name": "k", "lower": 0, "upper": 12}],
    "predicate": "k > n or comb(n, k) == comb(n, n - k)",
    "max_instances": 2000000
  }
}
```

```bash
python3 scripts/tiers/bounded.py --claim <claim.json> --json
python3 scripts/dialectic.py --claim <claim.json> --bound 12 --json
```

One variable or several — most small-case questions are about a pair, and a
single-axis sweep cannot express them. The bounds and the seed live in the
frozen claim and never on the command line, so a failing search cannot be
rescued by quietly shrinking the range.

Three outcomes, and they are three, not two: a counterexample (exit 1), an
exhaustive pass over the stated range (exit 0), and a budget stop before the
range was covered (exit 3, `UNKNOWN`). The third is neither of the others.
Record the bounds every time — outside them the search establishes nothing, and
that is true no matter how large the range was.

## Retrieval

Query the corpus for the exact declarations an approach would need, before
ranking it:

```bash
bash    scripts/build_corpus.sh --out corpus.json          # once per toolchain
python3 scripts/corpus.py query Nat.add_comm --corpus corpus.json
python3 scripts/corpus.py feasibility --queries <names.json> --corpus corpus.json --json
python3 scripts/premise_preflight.py --blueprint <plan.json> --corpus corpus.json
```

The index is built from the **elaborated environment**, not from a scan of
source files, and the difference is not marginal: the source scan finds 182,025
declarations where the environment holds 330,887 theorems. Everything produced
by an attribute, generated by a macro, or living in a core library outside the
scanned tree is missing from the first and present in the second — which is
where a large share of citable results actually live. On a six-name check the
environment index resolved 6 where the scan resolved 2.

So a name that "does not exist" against a source-scanned corpus may simply exist
somewhere the scan could not see. Check which index you are querying before
concluding a premise is absent, because the two answers differ and only one of
them is about Mathlib.

What comes back is one of:

- **known premise** — exists in Mathlib with a resolved name, type, and import;
- **search target** — plausibly exists but is unresolved;
- **absent** — would have to be established first, which is a sub-claim, not a
  citation.

Never assume a premise exists because it *should*. A guessed declaration name is
not evidence, and an approach resting on one is unranked until resolved. Record
rejected candidates with the exact blocking reason — a wrong name, a mismatched
type, an unmet precondition — so the same bad retrieval does not recur.

An empty corpus result is information. It usually means the formulation does not
match how the library states the concept, which is a reframing signal.

`premise_preflight` is the cheap version of the expensive question. The kernel
tier costs about five seconds per run, essentially all of it import elaboration,
and a plan citing a name that does not resolve will spend that five seconds to
learn what a lookup answers for free. Run it before every kernel attempt, not
after the first failure.

## Choosing a tier

Pick the cheapest tier that can reach the status the claim needs:

| Need | Tier | Ceiling |
|---|---|---|
| Is the shape even coherent? | `structural` | `SKETCH` |
| Does it hold for small cases? Is there a counterexample? | `bounded` | `CHECKED_BOUNDED` |
| Establish it outright | `kernel` | `VERIFIED` |

Freeze the choice before Generator starts, so a failed kernel attempt cannot be
downgraded to a bounded check and reported as if it were the same result.

Never open at `kernel` because the problem "looks hard". The cheap tiers are
also the fastest way to learn *how* it is hard, and formalizing early is a
microscope — it exposes missing definitions, wrong quantifier order, and
unavailable dependencies long before it proves anything.

## Ranking

`expected_value = target_fidelity × P(completion) × checkability`, ranked by gain
per unit cost. Two of the three terms are computable here, and an equation whose
inputs are all guesses is a guess with an equation next to it:

```bash
python3 scripts/corpus.py feasibility --queries <names.json> --corpus corpus.json --json
python3 scripts/feasibility.py --state <state.json> --json
python3 scripts/attackability.py --target <claim.json> --json
python3 scripts/lanes.py rank --state <state.json>
```

- **`checkability`** is the corpus resolution rate for the premises this
  approach names, plus whether the statement is expressible without inventing a
  definition. `corpus.py feasibility` returns the first as a fraction over the
  exact name list, so it is a measurement rather than an impression. An approach
  resting on three names of which one resolves is not "probably fine".
- **`P(completion)`** takes its formalization component from `feasibility.py`,
  which scores whether the thing can be encoded at all and at what cost —
  separately from whether it is true and separately from whether it is worth
  doing. Those three get conflated by every intuition and by no script.
- **`target_fidelity`** is yours. It is the judgement that cannot be delegated:
  does this approach, if it works, establish the frozen target — or something
  adjacent that will read like it in a report?

Rank with `lanes rank`, which also reports how many distinct method families the
portfolio holds. Method families count as distinct only if the *key method*
differs — extremal, probabilistic, algebraic/spectral, constructive,
induction/descent, reduction/gadget, analytic. Two arguments that differ only in
manipulation are one family, and the count is the thing to look at before
declaring a target hard.

## Proposing a decomposition

```bash
python3 scripts/decompose.py --claim <claim.json> --top 3
python3 scripts/sketch_rubric.py --sketch <sketch.json> --json
```

The pack could render a plan, check a plan, and score whether a plan's gaps were
good ones, and could not PROPOSE one — so the first creative step in the loop
was the only one with no tooling, and the rubric that exists to compare two
decompositions had never had two to compare.

`decompose` reads the shape of the frozen target and emits candidates: DIRECT
when there is nothing to exploit, CHAIN over the hypotheses, BRIDGE when the
conclusion relates two sides the hypotheses only relate through a middle,
CASES, INDUCTION. It ranks them with the same rubric that judges a hand-written
plan.

It proposes; the rubric ranks; **you choose and the kernel decides**. A high
score is not a reason to run a decomposition you think is wrong. And a target it
cannot parse returns `not_parseable` rather than a plausible plan about the
wrong goal — which no gate downstream would catch, because such a plan is
internally coherent.

## When to stop triaging

Triage has its own budget and it is the one nobody sets. Three stop conditions:

- **Two ranked lanes with distinct method families, both with resolving
  premises.** That is enough to start. A third candidate improves the portfolio
  far less than the first work item does, and the ranking of unstarted lanes is
  the least reliable number in the campaign.
- **The ranking stops changing.** If a further hour of retrieval moves no lane
  past another, the remaining uncertainty is not the kind retrieval resolves.
- **Every lane blocks on the same missing premise.** Then the premise is the
  claim. Freeze it as a sub-claim and triage that instead — continuing to rank
  routes through it is ranking the same obstacle repeatedly.

`python3 scripts/next_action.py --state <state.json>` returns exactly one action
in a fixed order when the choice is genuinely unclear. Long campaigns die on
turn discipline more often than on the mathematics, and a role that re-triages
because triage is comfortable is the common way that happens.

## Handing to the Researcher

Beyond the frame's work item, include: the variant/status ledger (what is known
for neighbouring statements), best known bounds with sources, obstructions
already recorded, precondition gaps found during retrieval, counterexample
pressure from the bounded pass, and the smallest tractable products worth
having.
